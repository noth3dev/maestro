# 크루가 실제 팀처럼 일하는 방식 — 설계 제안

상태: 진행 중 · 2026-09-26 (운영자 피드백 반영: 스카우트 제외, 전문 분야 관점 비판, 사용자에게 자주 묻기)

## 1. 지금 구조 요약

- **대화 표면:** 운영자(Conductor)는 Concertmaster 세션 채팅 하나에서 일한다. Overture 크루는 같은 채팅에 참여하고, 결과물은 세션 작업 폴더(git)에 파일로 남는다.
- **실행 조직:** 계약이 시작되면 영구 부서(Product/Design/Engineering/Security/…)의 Head가 깨어나 봉인 제출 → 토론 → Department Plan → Mission Bundle → Worker 실행 → 독립 인증(Quality/Encore/Metronome) 순서로 진행된다.
- **이번에 생긴 것:** 역할별 담당 영역(lead는 조율, 전문 작업은 담당 크루에게 넘김), @멘션 호출, 판단 단계(자발적 참여 최대 2명), 크루끼리 호출(메시지당 최대 6답), 도구 사용 표시, 형식별 산출물(HTML/SVG/MD).

실제로 돌려 보니 lead가 전부 혼자 처리하던 문제는 역할 담당을 명확히 하자 해결됐다(lead → @design 시안, @security 검토). 남은 문제는 "누가 무엇을 책임지고, 언제 비판하고, 언제 사람에게 묻는가"가 규칙으로 정해져 있지 않다는 점이다.

## 2. 원칙

1. **역할은 성격이 아니라 책임이다.** 역할마다 "소유하는 산출물"이 있다. 파일에는 주인이 있고, 주인이 아닌 역할은 고치지 않고 의견을 단다.
2. **만든 사람이 스스로 통과시키지 않는다.** Maestro의 "자기 인증 금지" 원칙을 기획 단계에도 그대로 적용한다. 계획과 task.md는 작성자가 아닌 역할의 검토를 거쳐야 계약이 된다.
3. **사용자와 자주 주고받는다.** 각 역할은 자기 분야의 결정이 필요할 때마다 운영자에게 직접 묻는다. 한 번에 한 가지, 선택지 2~3개와 추천안을 붙인다. 추측으로 진행하기보다 일찍 묻는 편을 택한다.
3-1. **모두가 자기 관점으로 본다.** 누가 계획이나 결과물을 올리면, 그 분야에 닿는 역할이 자기 관점(보안→보안, 디자인→UI/UX, 아키텍처→기술 구조)에서 문제를 짚고, 빠진 것을 채우고, 필요하면 묻는다. 전문 조사도 각 역할이 직접 한다(별도 리서치 역할 없음).
4. **대화는 조율용, 파일은 결과물.** 채팅에는 요청·결정·요약만 남기고, 내용은 파일에 쓴다.
5. **보이는 것이 곧 신뢰다.** 누가 무엇을 맡았고, 무엇을 했고(도구 사용), 무엇이 남았는지가 항상 화면에 보여야 한다.

## 3. 계획을 쪼개는 방법

세 단계로 고정한다. 각 단계는 "독립적으로 검증 가능한 결과" 단위로 나눈다. 계층(UI/서버/DB)이 아니라 결과 기준이다.

| 단계 | 파일 | 기준 | 주인 |
| --- | --- | --- | --- |
| 전체 계획 | `plan00.md` | 목표, 완료 정의(Definition of Done), 범위/비범위, 마일스톤 목록 | lead |
| 페이즈 | `plan01.md` … | 사용자에게 보이는 하나의 결과. 자체 인수 기준, 담당 부서, 선행 페이즈 | task editor |
| 슬라이스 | `plan01-slice01.md` … | Worker 한 명, Mission Bundle 하나로 끝나는 크기. 검증 방법(테스트/증거)이 명시됨 | task editor + 해당 부서 Head |

쪼개는 규칙:
- 슬라이스는 **혼자 검증 가능**해야 한다. "다른 슬라이스가 끝나야 확인 가능"하면 너무 잘게 쪼갠 것이다.
- 슬라이스는 **하나의 부서**가 책임진다. 두 부서가 필요하면 두 슬라이스로 나누고 의존성을 적는다.
- 의존성은 파일 머리의 `depends-on:` 목록으로 명시하고, 순환은 허용하지 않는다(DAG).
- 크기 상한(초안): 슬라이스당 예상 변경 파일 10개, 예상 Worker 턴 30회. 넘으면 task editor가 다시 쪼갠다.
- 슬라이스 단계는 계약 전에 전부 쓰지 않는다. 계약에는 plan00 + 페이즈까지, 슬라이스는 실행 단계에서 부서 Head가 Department Plan으로 확정한다(지금 구조의 Head Council과 자연스럽게 이어짐).

## 4. 비판(리뷰)이 필요한가

필요하다. 다만 매번 무겁게 하지 않고 **위험도에 따라** 켠다.

제안: **Plan Reviewer(비판 담당) 역할을 새로 둔다.** 보안 담당은 "보안 관점의 전문가", Plan Reviewer는 "계획 자체의 허점"(목표 불일치, 빠진 요구, 검증 불가능한 인수 기준, 과도한 범위, 숨은 비용)을 보는 반대 입장 담당이다. 사람 팀의 "까다로운 시니어 리뷰어"에 해당한다.

| 상황 | 리뷰 |
| --- | --- |
| 잡담, 질문, 작은 수정 | 없음 |
| 일반 기획(plan00/페이즈 작성·개정) | Plan Reviewer 가벼운 검토(블로커/제안 구분) |
| 데이터 경계, 외부 효과, 결제, 되돌리기 어려운 작업, 예산 상한 초과 | Plan Reviewer + Security 필수 |
| task.md → 계약 직전 | **리뷰 게이트:** 작성자가 아닌 역할의 "블로커 없음" 확인이 있어야 "계약 만들기" 버튼 활성화 |

리뷰 결과는 `reviews/<대상>.md`에 쓰고, 블로커는 채팅에 요약된다. 블로커는 해결되거나 운영자가 명시적으로 "감수"해야 닫힌다. 이 기록은 계약 증거에 포함된다.

## 5. 협업 방식 (채팅 규칙)

1. **요청은 추적한다.** `@role`로 한 요청은 "할 일 카드"(열림/완료)로 패널의 작업 보드에 보인다. 요청이 사라지지 않게 하고, lead가 라운드마다 정리한다.
2. **라운드 요약.** 크루 답변이 끝나면 lead가 3줄 요약을 남긴다: 결정된 것, 운영자에게 물을 것, 다음 할 일. 결정은 `decisions.md`에 누적된다(나중에 부서 Head가 읽는 맥락).
3. **질문은 각자, 자주.** 각 역할이 자기 분야 결정을 운영자에게 직접 묻는다(한 번에 하나, 선택지와 추천안 포함). lead는 라운드 요약에서 아직 열린 질문을 정리한다.
4. **공식 승인 지점은 셋:** ① 목표와 완료 정의 확인, ② 계약 승인(리뷰 게이트 통과 후), ③ 실행 중 critical 액션 승인. 그 사이의 분야별 질문은 자유롭게 오간다.
5. **상한과 비용.** 메시지당 크루 답변 최대 8, 관점이 닿는 역할 자발 참여 최대 3(현재 구현). 역할별 모델 등급은 Ensemble Router로: lead·Plan Reviewer는 추론이 강한 모델, research·design 초안은 가벼운 모델.

## 6. 기획 크루 → 실행 부서로 이어지게

기획 크루의 역할과 실행 부서를 짝지어 맥락이 끊기지 않게 한다.

| Overture 역할 | 실행 단계 담당 부서 |
| --- | --- |
| design specialist | Design Department |
| architecture analyst | Engineering Department |
| security evaluator | Security Department |
| task editor / plan reviewer | Product Department / Quality Department |

계약 시점의 작업 폴더(커밋 고정)가 부서 Head들의 공통 입력이 된다. Head의 봉인 제출은 "해당 역할이 쓴 파일 + 리뷰 기록"을 필수로 읽는다.

## 7. 화면

- 채팅: 크루 메시지 + 도구 사용 줄(구현됨) + 라운드 요약 카드.
- 패널 탭: **파일**(구현됨) / **작업 보드**(요청 카드, 리뷰 블로커) / **결정 로그**.
- `task.md` 탭: 리뷰 게이트 상태(블로커 수)와 만들기→확인→시작 버튼(구현됨, 게이트 추가 예정).

## 8. 구현 순서 (제안)

1. Plan Reviewer 역할 추가 + 위험도 기반 리뷰 규칙 + `reviews/` 규칙.
2. 리뷰 게이트: 계약 생성 시 서버가 "작성자가 아닌 역할의 블로커 없음"을 확인(증거에 포함).
3. lead 라운드 요약 + `decisions.md` + 질문 묶기.
4. 요청 추적(작업 보드) — @요청을 이벤트로 저장하고 패널에 표시.
5. 계획 3단 구조 규칙(plan00/페이즈/슬라이스, `depends-on`, 크기 상한)을 task editor 프롬프트와 계약 파서 검증에 반영.
6. 역할 ↔ 부서 연결: 계약 시 작업 폴더 커밋을 Head 활성화 맥락으로 전달.

## 9. 결정 기록

- Plan Reviewer: 새 역할로 추가(구현됨, taxonomy v3).
- 리뷰 게이트: 계약 생성 시 항상 적용, 운영자가 명시적으로 감수하면 예외(구현됨, 증거에 기록).
- 리서치 스카우트: 제외. 각 역할이 자기 분야를 직접 조사(ID는 기존 기록 호환용으로만 유지). 웹 검색 도구는 아직 없음 — 외부 capability로 따로 켜야 함.
- 질문: lead가 묶지 않고 각 역할이 직접, 자주 묻는다.

## 10. 남은 결정

1. Plan Reviewer를 **새 역할**로 둘지, 기존 역할(예: task editor)에 "상호 검토 의무"만 줄지.
2. 리뷰 게이트를 **항상** 걸지, 위험도가 있을 때만 걸지.
3. 슬라이스를 계약 전에 쓸지(지금 제안: 계약 후 부서 Head가 확정).
4. 운영자 결정 지점을 위 3개로 줄이는 데 동의하는지.
